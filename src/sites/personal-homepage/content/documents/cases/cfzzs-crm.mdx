<ArchiveSection id="workflow" title="CRM 的核心是状态可信，而不是表格数量。" eyebrow="01 / 工作流">

线索、联系人、企业、跟进记录和园区空间必须在同一权限模型下协作。仪表盘只是结果，服务端数据范围才是产品骨架。

这个项目一开始最像一张很大的表：字段很多，页面也可以继续加。但招商团队真正需要的不是更多输入框，而是知道这条线索现在由谁负责、下一步是什么、这次修改有没有影响别人。于是我先把实体关系和阶段流转画出来，再决定哪些信息应该在同一屏出现。

查重和空间资源也是同一个问题的另一面。企业名称相同不代表一定是同一家公司，空间状态也不能只靠前端颜色判断。把判断放到服务端，页面才不会因为不同人的缓存而讲出两套故事。

</ArchiveSection>

<ArchiveSection id="concurrency" title="阶段流转用乐观锁保护。" eyebrow="02 / 并发">

多人同时编辑时，旧版本更新会被拒绝并要求重新读取，避免后提交的人悄悄覆盖现场信息。

冲突提示必须是业务语言，而不是一句“保存失败”。用户需要知道谁先改了哪一类信息，以及自己可以重新确认还是需要找负责人处理。版本号藏在接口里，冲突理由应该出现在界面里。

</ArchiveSection>

<ArchiveSection id="delivery" title="生产验收覆盖真实角色动作。" eyebrow="03 / 交付">

E2E 不只检查页面能开，还覆盖登录、业务路由、后台路由、用户创建与 CSV 导入。

验收脚本按角色走完整动作：登录后能看到什么，创建线索后能推进到哪里，越权请求会被挡在哪里，导入失败时是否留下可理解的反馈。这样查出来的问题才接近上线后的问题，而不是只证明几个 URL 返回了 200。

</ArchiveSection>

</LocaleBlock>

<ArchiveSection id="workflow" title="A CRM is only as good as its trustworthy state." eyebrow="01 / Workflow">

Leads, contacts, companies, follow-ups, and spatial inventory must cooperate under one permission model. The dashboard is an output; server-side scope is the product skeleton.

At first the project looked like a large table with room for more fields. The team did not really need more inputs; they needed to know who owned a lead, what came next, and whether a change affected somebody else. I mapped the entities and stage transitions first, then decided what deserved to share a screen.

Deduplication and spatial inventory are the same problem in another form. A matching company name is not proof of identity, and a space cannot be trusted because a front-end color says it is free. Keeping those decisions on the server prevents different cached pages from telling different stories.

</ArchiveSection>

<ArchiveSection id="concurrency" title="Optimistic locking protects stage transitions." eyebrow="02 / Concurrency">

When multiple operators edit the same lead, stale updates are rejected and refreshed instead of silently overwriting field intelligence.

The conflict message has to use business language, not only “save failed”. An operator needs to know what changed and whether a fresh confirmation is enough or an owner needs to be involved. The version belongs in the API; the reason belongs in the interface.

</ArchiveSection>

<ArchiveSection id="delivery" title="Production acceptance follows real role actions." eyebrow="03 / Delivery">

E2E checks more than page availability: login, business and admin routes, user creation, and CSV import are exercised.

The acceptance flow follows roles and complete actions: what is visible after sign-in, where a lead can move, where an unauthorized request is stopped, and whether a failed import leaves a useful explanation. That catches problems closer to production than proving a few URLs return 200.

</ArchiveSection>
