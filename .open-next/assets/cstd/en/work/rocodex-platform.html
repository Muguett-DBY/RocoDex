01 / Problem

A shared deployment is not a shared product.

custard.top and RocoDex serve different audiences with different routes and runtime needs. Co-location was not the risk; undocumented ownership was.

  • The portfolio must not initialize the encyclopedia auth context.
  • The wrong host must never expose pages owned by the other product.
  • Each site needs its own browser regression and SEO output.

Putting both products in one repository first looked like a deployment convenience. The portfolio needs room for personal expression and visual experiments; the encyclopedia needs stable search, collection, and team data. Shared infrastructure is useful. Shared product state by default is not.

02 / Architecture

Host decisions happen before rendering.

The proxy chooses rewrite, redirect, pass-through, or 404 by host. Route groups then express ownership, while each site exposes only a narrow public API.

The order solves a concrete problem: when someone visits custard.top, the encyclopedia auth, data APIs, and page tree are never initialized. The reverse is true for rocodex.custard.top; a similar path in the portfolio cannot catch the request. The host routes first, React renders second, and the wrong product never gets a chance to start.

03 / Decision

Tests enforce what folders alone cannot.

Architecture tests scan production imports, block cross-site dependencies, and keep the Three.js runtime confined to its lazy scene boundary.

That makes “the portfolio is the portfolio, and RocoDex is RocoDex” more than a folder note. When a new page, auth path, or data module is added, the test turns a boundary crossing into a concrete failure. Maintainers do not have to remember every import that is forbidden.
